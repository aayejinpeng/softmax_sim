# 开题报告第二点：面向 AICPU 的有限乱序向量单元升级

## 研究定位

本课题的第二个研究点，聚焦于在 Saturn / Titan-I 这类有限乱序向量单元上继续升级，让向量执行在不复制大核级 SIMD 后端的前提下，获得接近高效乱序执行的吞吐能力。这里的核心不是把 AICPU 做成一颗“缩小版高性能 CPU”，而是围绕 AICPU 的负载特征，设计一种成本更可控、实现更清晰的有限乱序执行机制。

## 问题背景

传统高性能 CPU 为了最大化通用单线程性能，通常采用向量寄存器重命名、大容量向量物理寄存器堆、深调度队列和复杂旁路网络。这类方案能够提供强大的向量乱序执行能力，但面积、功耗和验证复杂度都很高。对于 AICPU，更合理的方案是采用有限乱序、scoreboard 或访存/计算解耦机制，在保留足够延迟隐藏能力的同时，避免复制大核级 SIMD 后端。

因此，本课题的关键不是“是否乱序”，而是“乱序做到什么程度、以什么代价做到、为哪些并行模式服务”。对于 softmax、rmsnorm、silu、rope 这类算子，真正需要的是在有限窗口内发现独立的向量操作、隐藏局部访存和函数近似延迟，并让多个 head、row 或 lane 的工作尽量交错推进，而不是盲目追求大核式的重调度规模。

## 已有基础

本课题已经具备三层基础。

第一层是微结构实验。当前模拟器已经支持 in-order / out-of-order 两种发射模式，支持 issue queue window、scheduler window、issue width、lane 数量和寄存器重命名开关等参数，并能够直接统计 cycle、speedup 和各类部件利用率。这使得“有限乱序是否有效、窗口大小多大合适、重命名是否值得引入”可以被量化比较，而不是停留在概念层。现有结果也说明，OOO 的收益是有边界的，小窗口配置并不总能稳定压过顺序发射。

第二层是 ISA 设计。已有的 ISA 方案已经引入了面向多 lane 的执行语义，包括 lane 视角、stride 选择和逻辑寄存器映射等机制。它提供了把多个独立计算流显式暴露给硬件的接口基础，也为后续的编译器协同提供了落点。

第三层是编译流程设计。已有编译流程能够把算子拆成可调度的向量指令序列，并为不同硬件参数生成对应的 benchmark 配置。也就是说，软硬件协同的链条已经基本闭合，接下来要做的是在这个链条上把“有限乱序”真正做深、做实。

## 实验依据

现有 benchmark 结果已经说明，有限乱序确实有帮助，但它不是无条件的加速器。小窗口、无重命名的配置往往只能接近顺序发射，只有当窗口逐步增大、并结合重命名或展开时，吞吐才会更明显地抬升。

| kernel | in-order baseline | best no-rename limited OOO | best with rename | 观察 |
| --- | ---: | ---: | ---: | --- |
| softmax_fma_exp_approx | 32522 | 5026 | 4349 | 小窗口 OOO 并不总能胜过 in-order，窗口拉大后才逐步体现收益，重命名提供更高上界 |
| softmax_exp2_unit | 30474 | 3398 | 2929 | EXP2 路径下，OOO 的收益更依赖较大的 window，重命名更容易拉开差距 |
| rmsnorm | 5130 | 1690 | 503 | 长依赖链下有一定乱序价值，但窗口不足时效果有限，重命名更能放大收益 |
| silu_fma_exp_approx | 6026 | 1290 | 1176 | 收益存在但不夸张，较大的窗口和重命名才是主要上限来源 |
| silu_exp2_unit | 5514 | 1630 | 454 | OOO 有帮助，但提升不是无条件的，仍然受窗口和工作负载形态约束 |
| rope | 4234 | 1431 | 438 | 适合做交错推进，但并不意味着大 OOO 会带来指数级提升 |

从这些结果可以看到三个结论。

1. 仅靠顺序发射，很多算子确实难以充分隐藏局部延迟，但这并不自动意味着小窗口 OOO 就一定更快。
2. 有限乱序的收益高度依赖窗口大小和依赖形态，窗口太小或缺少重命名时，提升常常有限。
3. 重命名、循环展开和多 lane 交错会共同决定最终收益；更合理的目标不是复制完整大核 SIMD 后端，而是找出 AICPU 上“够用且划算”的窗口边界。

## 拟研究内容

本课题准备在 Saturn / Titan-I 类有限乱序向量单元上，研究一种“低代价高收益”的升级路径，核心包括以下几部分。

1. 重新定义有限乱序的边界。将 issue_queue_window 视为所有未提交指令的可见窗口，将 scheduler_window 视为在该窗口内参与竞争和调度的子窗口；in-order 和 out-of-order 的差别只体现在发射策略上，而不是是否能看到未提交指令。

2. 设计轻量级乱序发射机制。硬件只保留足够小的调度队列、scoreboard 和必要的依赖跟踪，不引入大规模向量物理寄存器堆、深层 wakeup/select 队列和完整 CPU 式旁路网络，并重点评估不同窗口下收益的拐点与饱和点。

3. 引入受限重命名或版本化映射。重命名不以“完全消除所有名字依赖”为目标，而是面向独立 head、lane 或计算片段进行选择性消除假相关，从而在成本可控的前提下提升并行度；它更像是放大器，而不是 OOO 的唯一来源。

4. 增强访存与计算解耦。对于多 lane 和多 context 场景，借助 stride、lane 视角和 load/store 语义，把可并行的访存和计算流拆开推进，减少长延迟操作对后续指令的阻塞。

5. 引入循环展开式 head/row 并行。编译器在不超过逻辑寄存器预算的前提下，把多个 head 或 row 展开到不同的逻辑寄存器银行中，再以交错顺序发射，从而在不依赖完整物理重命名的情况下暴露更多独立性。这个机制会显著压低纯硬件重命名的边际收益。

6. 形成编译器协同闭环。编译器将根据算子结构和硬件配置生成适配的指令序列、lane 配置、循环展开开关和调度提示，让硬件更容易在有限窗口中发现独立性；当展开开关打开时，自动按逻辑寄存器预算展开到最大。

## 预期贡献

本研究希望回答一个具体问题：对于 AICPU，有限乱序向量单元究竟怎样升级，才能在不付出昂贵乱序代价的情况下获得高效执行。

预期贡献主要有三点。

第一，给出一套适合 AICPU 的有限乱序向量微结构方案，而不是照搬高性能 CPU 的 SIMD 后端。

第二，形成 ISA、编译器和微结构协同设计的方法，使算子级并行性能够被更稳定地暴露给硬件。

第三，通过已有 benchmark 实验，建立一套可量化的评价体系，用 cycle、利用率和不同窗口配置下的性能变化，说明有限乱序与轻量重命名的真实价值边界，避免把“大 OOO”误判成万能方案。

## 可直接放入开题报告的表述

本课题拟面向 Saturn / Titan-I 一类有限乱序向量单元，研究一种低代价、收益可控的向量执行升级机制。与传统高性能 CPU 依赖的大规模向量寄存器重命名、深调度队列和复杂旁路网络不同，本课题更强调面向 AICPU 负载特征的有限乱序、scoreboard 和访存/计算解耦设计，在保持必要延迟隐藏能力的同时，避免复制大核级 SIMD 后端。基于已有的微结构实验、ISA 设计和编译流程，本课题将系统研究 issue queue window、scheduler window、轻量重命名以及多 lane 协同调度对 softmax、rmsnorm、silu、rope 等算子执行效率的影响，重点找出有限乱序的收益边界和最优窗口区间，形成一套可落地的软硬件协同优化方案。

进一步地，课题还将把循环展开与逻辑寄存器分银行作为编译器侧的重要手段：在逻辑寄存器总数不变的约束下，将多个 head 或 row 显式展开到不同寄存器银行中，并以交错方式组织发射顺序，使硬件能够在不引入昂贵物理重命名的情况下获得更多独立工作流。这样做的目的不是把 OOO 神化，而是把“有限乱序 + 编译器展开 + 轻量重命名”各自的作用边界分清楚。
